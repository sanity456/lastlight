# Build a branching GenLayer survival mission

LastLight is a small example of putting language judgment inside a game rule. The player describes a response to a fictional station emergency. GenLayer validators judge one specific criterion from that response, and ordinary contract code uses the agreed verdict to update the game. The model does not choose a score, alter a resource amount, or pick a payout.

## 1. Edit one source of truth

The authored mission lives in `content/kestrel-01.json`. It contains the rules version, initial oxygen, power and hull, plan limits, fixed changes for each verdict, reason-code descriptions, and three rounds. Each round has one criterion. Later rounds hold branch maps with their own title, facts, equipment, constraints, criterion, and power cost.

For example, round one maps `MET` to `steady_flow` and both other verdicts to `pressure_alarm`. The steady path opens a powered repair locker with a patch kit. The alarm path blocks that locker and provides a manual clamp. The contract stores the selected branch after each finalized action, so a browser refresh cannot change the path. Run `npm run generate` after editing the JSON. The generator serializes the rules into the Python contract and frontend and computes one SHA-256 hash used by both. Run `npm run check:content` to detect stale generated files.

## 2. Keep the contract authoritative

The contract starts with a pinned GenVM dependency. It stores session and round records in GenLayer maps as JSON strings. `create_session` creates a solo game or a named-wallet invitation. `join_session` permits only that invited wallet. The invitation has a fixed 72-hour deadline; after that, anyone may call `expire_invitation`. A host may cancel an unjoined invitation, and a crew member may abandon an active run.

`submit_plan` accepts the session ID, expected round, unique action ID, and public plan. The contract checks the turn, status, plan byte length, action replay, and power before it starts the judgment. The selected criterion and scenario facts come from the hashed mission rules, never from the plan. The plan is passed as untrusted text. The prompt explicitly ignores attempts inside the plan to change the evaluator's role, instructions, schema, or outcome.

The leader must return exactly three fields: `verdict`, `quote`, and `reason_code`. The verdict is one of `MET`, `NOT_MET`, and `INSUFFICIENT_EVIDENCE`. A reason code explains the finding using a small fixed vocabulary. The quote is limited in length and must occur verbatim in the plan. When the action is missing, the only valid reason is `ACTION_MISSING` and the quote is empty. This prevents a model from inventing evidence for an absent action.

## 3. Let validators check the substance

The custom validator does more than check JSON shape. It independently repeats the same narrow evaluation over the same immutable plan input and trusted criterion. After agreeing on verdict and reason code, it checks whether the leader's verbatim quote itself supports that finding. A quote that merely appears somewhere in the plan is insufficient. Each transaction asks one criterion, which keeps consensus focused and lets the reviewer inspect the exact question afterward.

After consensus, deterministic Python maps the verdict to fixed resource changes. A `MET` result earns a small fixed recovery; `NOT_MET` causes a larger setback; `INSUFFICIENT_EVIDENCE` causes a smaller setback than a contradiction. These values are authored in the mission file, not generated by the model. The contract clamps resources, ends the run if any resource reaches zero, selects the next branch, and calculates the final score from resource values and successful judgments.

## 4. Show the receipt to players and reviewers

The frontend reads the active branch from the contract and displays only its facts, available equipment, constraints, and single criterion. After finality it shows the result label, a human-readable reason-code description, the quoted excerpt, the full public plan behind a disclosure control, resource changes, and the branch chosen for the next round. It links to a round's explorer transaction when the hash is known locally or published in the proof manifest. The My Missions view is built from public contract reads. A pending transaction stays visible and can be rechecked instead of being submitted a second time.

The browser is a client, not the authority. It cannot change the verdict, branch, resource update, or final score. It requests a wallet signature for every write, attaches zero GEN, and links the deployed contract to the explorer. The contract address is accepted only if its `get_config` rules version and mission hash match the generated frontend rules.

## 5. Test honestly and finish the live proof

Run `npm run generate`, `npm run check:content`, `npm test`, `npm run build`, and `GENVM_VERSION=v0.2.16 .venv/Scripts/genvm-lint.exe check contracts/lastlight.py --json` (PowerShell uses `$env:GENVM_VERSION='v0.2.16'` before the linter command). Direct tests cover role checks, retry behavior, exact-quote validation, every verdict's fixed effects, branch selection, all verdict sequences, duo turns, and expired invitations. The direct test environment supplies mocked model output. It does not test validator agreement or demonstrate that hostile plan text is ignored by the live model.

Before presenting this milestone as live, deploy the v2 source to Studionet, then run a positive solo path, a contradictory or incomplete path that changes equipment, a prompt-injection attempt, and a duo path if time permits. Wait for finalized successful execution, read each session and round back from the public contract, and record the creation hash and all three round hashes for each case in `deploy/proof.json`. Publish the exact source commit. The proof verifier reads those public records and checks the pinned source, rules hash, finality, quoted evidence, and expected branches. Until those steps are recorded, label the work as locally tested only. Never describe a mock response as a live consensus result.
